# Sort a playlist in the browser with "Move to bottom", reloading after each move: no API quota

**Symptom**
The Vahagn playlist (`PLz3NrXxHz_CCqlI0X_XZvf4YOVuF2n_FM`, a YouTube "Course") showed newest first: the 25 new pieces
on top in upload order, then 20.3 -> 1.1. A section sort through the API (`playlistItems.update`, 50 units a move) needed
93 moves, ~4,650 units, on a day with ~5,000 already used (daily cap 10,000). `yt_publish.py sort-playlist --by lesson`
cannot order 23.1-ա / 23.1-բ anyway (whole lesson numbers only).

**What the browser offers (2026-10-27)**
- Studio's course page ("Course videos") has no reorder control: per row only "Remove from this course".
- The youtube.com playlist page, signed in as the owner channel, has per item More actions > "Move to top" / "Move to
  bottom". Rows are `yt-lockup-view-model`, the title is the `h3` link's text (not `ytd-playlist-video-renderer`).
  Its banner "This is how your playlist looks in American English. Switch to Armenian to make changes" concerns the
  playlist's text; the item moves work regardless.

**Gotchas**
- The newest-first view was an automatic sort over a different stored order. The first manual move switched the
  playlist to its stored order (20.3 -> 1.1, then the 25 in the order they were added): what the page showed before
  was not what "bottom" meant.
- The page does not redraw after a move: 1.2 moved, but the last row still read 1.1 until a reload. So: reload, check
  that the item just moved is last, move the next one.

**What worked**
For every item in target order: reload, More actions > Move to bottom. 97 moves in 891 s (~9 s each), then the API read
the playlist as 1.1 -> 28.4 with 0 moves left. Driver: `.playwright-mcp/vahagn_playlist_sort.js` (generated by the
session's scratch `make_sort_driver.py`). Quota used: 0 (only the 2-unit read to confirm).
